# الجزء الأول: خطة التشغيل والتحقق قبل الدمج إلى `main`

## 0) قاعدة العمل
- **لا دمج قبل أن يمر كل شيء.** هذه التعديلات كُتبت دون تشغيل أي اختبار، فنعاملها كأنها غير مختبرة.
- عند الفشل: نصلح **السبب**، لا نُضعف الاختبار. استثناء واحد: خطأ في الاختبار نفسه (نص/محدِّد) لا في السلوك.
- شغّل مجموعة الـ backend ومجموعة الواجهة **الواحدة بعد الأخرى**، لا معاً (توصية `backend/README.md`: قد تنتهي مهلة بعض اختبارات الواجهة على جهاز مشغول).

**2.3 نقاط تستحق نظرة إن فشل شيء**
| العَرَض | السبب المحتمل | الإجراء |

| فشل اختبار 429 في `change-password` | تحديد المعدّل في الاختبار يعتمد `RATE_LIMIT_SCALE=1` | تأكد أن `testApp({ env })` يمرّر القيمة؛ لا تغيّر الحد (5 محاولات/15 دقيقة) |

## 4) إن فشل اختبار واجهة: شجرة القرار
1. **اقرأ أول خطأ فقط** (غالباً ما بعده تابع له).
2. **فشل بسبب نص/محدِّد** (`Unable to find a label…`، `Found multiple elements…`):
   - الأسباب المعتادة: علامة `*` في تسمية الحقل الإلزامي، أو تطابق جزئي بين «كلمة المرور الجديدة» و«تأكيد كلمة المرور الجديدة».
   - الحل: عدّل **الاستعلام** في الاختبار (`getByLabelText(/^…/)` أو `{ exact: false }`) لا مكوّن الصفحة، ما لم يكن النص ناقصاً فعلاً في الواجهة.
3. **فشل بسبب ترتيب `import` أو lint** (`import/order`، `no-unused-vars`): أصلح الصياغة فقط (احذف المستورد غير المستخدم مثل `UserCircle` إن لم يُستعمل)، ثم أعد `npm run lint`.
4. **فشل بسبب البيئة** (`ReferenceError: document is not defined`، مهلة): تأكد من السطر `// @vitest-environment jsdom` في أول الملف، وأعد التشغيل منفرداً (`npx vitest run <ملف>`)، وأغلق أي خادم يشغل المنافذ.
5. **فشل سلوكي حقيقي** (طلب لم يُرسل، حقل خاطئ): هذا خلل في الكود، أصلحه وأضف اختباراً يغطيه.
6. بعد كل إصلاح: `git commit` صغير بعنوان واضح على نفس الفرع؛ لا `--amend` ولا `force push` بعد أن يصبح الفرع على GitHub.

## 5) التحقق اليدوي
شغّل البيئة:
```bash
cd backend && npm run migrate && npm run seed && npm run dev     # :4010
cd frontend && echo "API_URL=http://localhost:4010" > .env.local && npm run dev    # :3000
```
**أ) تغيير كلمة المرور** (حساب تجريبي من `docs/demo-accounts.md`)
1. سجّل الدخول من نافذتين (عاديّة + خاصة).
2. في الأولى: **حسابي** ← كلمة خاطئة ← يظهر خطأ تحت «كلمة المرور الحالية» ولا تتغير الكلمة.
3. كلمة صحيحة وجديدة تحقق الشروط ← رسالة نجاح؛ الجلسة الأولى تبقى، والثانية تُطرد عند أول طلب (401 ← صفحة الدخول).
4. الدخول بالكلمة القديمة يفشل وبالجديدة ينجح.
5. البريد: بالتطوير يُحفظ في `outbox` (transport "console") — استعمل `GET /__control/mail` في وضع e2e أو سجل الخادم؛ الموضوع «تم تغيير كلمة مرور حسابك - مسار».
6. 5 محاولات بكلمة حالية خاطئة ← السادسة 429.
7. عبر curl (مباشرة على الـ backend):
```bash
T=$(curl -s localhost:4010/login -H 'content-type: application/json' \
  -d '{"admin_email":"<email>","admin_password":"<pass>"}' | jq -r .token)
curl -i localhost:4010/auth/change-password -H "authorization: Bearer $T" -H 'content-type: application/json' \
  -d '{"current_password":"x","password":"New#Pass2","password_confirmation":"New#Pass2"}'   # 422 على current_password
```
**ب) قرارات المشغّل والتدقيق**
1. سجّل منظمة جديدة وأكمل التهيئة، ثم من لوحة المشغّل (أو `npm run cli`) ارفض ثم اعتمد ثم علّق.
2. تحقق من القاعدة:
```sql
select id, organization_id, actor_id, action, entity_type, entity_id, meta, created_at
from audit_logs order by id desc limit 10;
```
المتوقع: `organization.rejected / approved / suspended`، و`actor_id` = المشغّل، و`meta` فيها السبب، **ولا توجد أي كلمة مرور في `meta`**.
3. صف `auth.password_changed` يظهر بعد تغيير كلمة المرور (لحسابات المنظمات؛ مشغّل المنصة لا منظمة له فلا صف).

**ج) الـ BFF عبر المواقع**
```bash
curl -i -X POST localhost:3000/api/auth/logout -H 'Origin: https://evil.example'   # 403
curl -i -X POST localhost:3000/api/auth/logout -H 'Origin: http://localhost:3000'  # 200
curl -sI localhost:3000/ | grep -iE 'x-frame|nosniff|referrer|permissions|strict-transport'
```
وفي المتصفح: صفحة محلية على منفذ آخر تعمل `fetch('http://localhost:3000/api/…',{method:'POST',credentials:'include'})` يجب أن ترفض (CORS/403).

## 6) الانتقال الآمن إلى `main`
1. **دفع الفرع** (تم) وفتح Pull Request: `audit/security-hardening → main`.
2. **CI**: الوظائف الثلاث خضراء (backend/SQLite، backend/PostgreSQL، frontend). هذه أول مرة تعمل فيها اختبارات الـ backend في CI، فقد تظهر مشاكل بيئة خاصة بـ CI (إصدار Node، خدمة PostgreSQL)؛ أصلحها في الـ workflow لا بتعطيل الوظيفة.
3. **مراجعة الفرق**: `git diff main...audit/security-hardening --stat` — لا ملفات سرّية ولا `.env`.
4. **الدمج**: *Squash and merge* (تاريخ نظيف) أو *Merge commit* (يحفظ التفاصيل)؛ كلاهما مقبول. لا `force push` على `main`.
5. **بعد الدمج**: شغّل `npm test` على `main` مرة أخيرة، ثم احذف الفرع.
6. **التراجع**: `git revert <merge-sha>` (آمن لأن لا migration جديدة في هذا الفرع — لا حاجة لتراجع قاعدة البيانات).
7. اقتراح: فعّل *Branch protection* على `main` (CI إلزامي + PR مطلوب) حتى لا يتكرر وضع «CI لا يشغّل الاختبارات».

> **عدّ الاختبارات الجديدة:** backend: 8 (`change-password.test.js`) · الواجهة: 5 (`account.test.jsx`) + 10 (`csrf.test.js`، منها حالات `it.each`) + 3 (`routes.test.js`) = 18.

# الجزء الثاني: بنك أسئلة لجنة المناقشة

## أ) المعمارية والقرارات التصميمية

**س1: لماذا فصلتم الواجهة عن خادم Fastify بطبقة BFF داخل Next.js؟**
لسببين. (1) **أمني:** رمز الجلسة يُحفظ في كوكي `HttpOnly` يضعه خادم Next، فلا يصل إلى JavaScript المتصفح، فلا تسرقه ثغرة XSS. المتصفح يكلّم `/api/*` على نفس الأصل، والـ BFF يضيف `Authorization: Bearer` ويمرّر الطلب للـ backend. (2) **معماري:** الـ backend يبقى API نقياً بلا كوكيز ولا CORS، فلا سطح CSRF مباشر عليه ويصلح لعملاء آخرين (تطبيق جوال مثلاً) بالرمز نفسه. الثمن: قفزة شبكية إضافية وطبقة يجب حمايتها (فأضفنا فحص `Origin`).

**س2: لماذا Fastify وKnex وليس إطاراً أثقل؟**
Fastify سريع ويفرض مخططات واضحة؛ نستعمل Zod للتحقق. Knex يعطي استعلامات صريحة وهجرات (migrations) ويعمل على SQLite للتطوير والاختبار السريع وعلى PostgreSQL للإنتاج، وكل الاختبارات تمر على الاثنين. اخترنا البساطة والقابلية للتدقيق على «السحر» الذي يخفي الاستعلامات.

**س3: كيف يتحقق عزل بيانات المنظمات؟**
كل جدول أعمال فيه `organization_id` إلزامي (`NOT NULL` عبر `tenant(t)` في الهجرات)، والاستعلامات تُقيَّد به من سياق المصادقة (`request.auth.organizationId`) لا من مدخلات العميل. العميل لا يرسل معرّف منظمته أبداً. اختبارات التكامل تتحقق أن مستخدماً من منظمة لا يرى سجلات أخرى.
**حد صريح:** العزل في طبقة التطبيق والقيود، وليس Row-Level Security في PostgreSQL. لذا خطأ برمجي في استعلام جديد قد يكسره؛ والحماية هي النمط الموحّد والاختبارات. RLS خيار تحسين مستقبلي.

**س4: ولماذا إلزام `project_id` للجداول التشغيلية؟**
المنظمة وحدها حدّ خشن؛ داخلها فرق مشاريع تختلف صلاحياتها. الهجرتان 11 و12 جعلتا `project_id` إلزامياً، والوصول يمر عبر `assertProjectAccess`/`projectRoleOf` بأدوار (admin/supervisor/member). غير العضو يحصل على **404 لا 403** كي لا يُكشف وجود المشروع أصلاً.

**س5: ما الفرق بين صلاحية المنظمة وعضوية المشروع؟**
الصلاحية (23 مفتاحاً مثل `requests.view`) تقول *ما نوع الأفعال* المسموحة. العضوية تقول *في أي مشروع*. الفعل مسموح فقط إن اجتمع الاثنان. الواجهة تخفي العناصر حسب الصلاحيات لكن هذا عرض فقط؛ الفرض الفعلي في `app.guard` بالـ backend.

## ب) الأمان والصلاحيات

**س6: كيف تحمون الجلسات؟**
الرمز عشوائي معتم (`mt_…`) وليس JWT؛ نخزّن منه **SHA-256 فقط**، فتسريب قاعدة البيانات لا يعطي جلسات صالحة. صلاحيته 30 يوماً، ويمكن إبطاله فوراً (تسجيل الخروج يحذف الصف). تغيير كلمة المرور يحذف **كل الجلسات الأخرى** للمستخدم داخل نفس المعاملة، وتبقى الجلسة الحالية. ميزة المعتم على JWT: الإبطال الفوري دون قائمة سوداء.

**س7: وكلمات المرور؟**
تجزئة scrypt بملح، وسياسة (8 أحرف+رقم+رمز) تُفرض في الـ backend ويعكسها نموذج الواجهة. لا نكشف إن كان البريد موجوداً (تسجيل الدخول لمستخدم غير موجود يحسب تجزئة وهمية بزمن مماثل). رموز التحقق 6 أرقام مجزّأة بمفتاح HMAC، بحد 5 محاولات لكل رمز، وتحديد معدّل للإرسال.

**س8: ماذا يضيف `POST /auth/change-password` أمنياً؟**
(1) يطلب **الكلمة الحالية** كي لا تكفي جلسة مسروقة لاستلاب الحساب. (2) محاولات الحالية الخاطئة محدودة: 5 كل 15 دقيقة **لكل مستخدم** (لا لكل IP فقط) فلا يُستعمل المسار لتخمينها. (3) رفض كلمة مطابقة للقديمة. (4) إنهاء الجلسات الأخرى. (5) صف تدقيق وبريد إشعار للمالك ليكتشف التغيير غير المصرّح. وكلها في معاملة واحدة.

**س9: كيف تمنعون CSRF؟**
طبقات: كوكي `SameSite=lax` (لا يُرسل في POST عبر المواقع)، ثم في الـ BFF فحص `Origin` لكل طلب مغيِّر (وبديله `Sec-Fetch-Site`)، ويشمل الدخول والخروج (منع login CSRF). والـ backend نفسه لا يعتمد على كوكيز أصلاً. الطلبات بلا أيٍّ من الترويستين (curl/خادم لخادم) مسموحة لأنها لا تحمل كوكيز ضحية.

**س10: لماذا أجّلتم CSP؟**
لأن Next يحقن سكربتات مضمّنة؛ سياسة CSP مفيدة تتطلب **nonce لكل طلب** عبر `proxy.js` وتحويل الصفحات إلى رندر ديناميكي، وهذا يمس الأداء والبنية ويحتاج اختباراً شاملاً. سياسة مع `'unsafe-inline'` تعطي إحساساً زائفاً بالأمان. بدلاً منها فعّلنا ما لا يكسر شيئاً (nosniff، منع التضمين، HSTS، Referrer/Permissions-Policy). وتبقى وقاية XSS: هروب React التلقائي وكوكي HttpOnly. بند مجدول لا منسي (تقرير التدقيق §4).

**س11: ما أكبر مخاطرة متبقية؟**
(1) محدِّد المعدّل في ذاكرة كل عملية: تشغيل أكثر من نسخة يضاعف الحدود الفعلية؛ الحل مخزن مشترك. (2) التدقيق يغطي عمليات محدودة (دور الموظف، قرارات المشغّل، تغيير كلمة المرور) ولا يغطي الطلبات/الملفات. (3) غياب CSP. (4) الملفات على قرص محلي. كلها موثقة في التقرير و`backend/README.md`.

## ج) جودة الهندسة والاختبارات والأمانة العلمية

**س12: لماذا فرع `audit/security-hardening` منفصل؟**
ليبقى `main` صالحاً للنشر؛ فالتعديلات أمنية وتمس المصادقة والـ BFF، وتحتاج مراجعة ودورة CI قبل الدمج. الفرع يتيح مراجعة فرق واضح (PR) والتراجع بـ `git revert` دون المساس بالتاريخ، وهو يعكس الممارسة المهنية: لا تعديل أمني مباشر على الفرع الرئيسي.

**س13: سلّمتم تقريراً يقول إن الاختبارات الجديدة لم تُشغَّل. كيف تبرّرون ذلك؟**
الأمانة العلمية تقتضي ألا أدّعي نجاحاً لم أره. البيئة التي كُتب فيها الكود بلا شبكة ولا `node_modules` ولا Docker. الذي أثبتّه فعلاً وبالتشغيل: تجميع كل ملفات المشروع (backend و230 ملف واجهة) بلا أخطاء استيراد، وESLint نظيف على الملفات المعدّلة، ومخطط `changePasswordSchema` الحقيقي على 7 حالات (7/7)، واختبارات CSRF العشرة وclient-ip الستة والثلاثين تحت مُحاكٍ بسيط لـ vitest. وما لم أشغّله (Vitest الحقيقي، التكامل مع Fastify/Knex، PostgreSQL، RTL، `build`) مصرَّح به في `AUDIT_REPORT.md`. ما لم يثبت صُرّح بأنه غير مثبت، وحُدّد له **معيار قبول قابل للقياس**: ≈507 اختبار backend على SQLite وعلى PostgreSQL، ≈464 للواجهة، و`lint` و`build`، ثم ثلاث وظائف CI خضراء، ولا دمج قبل ذلك. الخطر الأكبر هو ادّعاء غير مثبت، لا اعترافٌ بحدّ.
والمرجع الأساس لجودة المشروع: الأرقام السابقة (499/446 بتاريخ 2026-11-18 وتحققها على PostgreSQL 17) مسجلة بتاريخها، وليست مجددة بعد هذه التعديلات.

**س14: كيف تضمنون أن الاختبارات الجديدة تختبر شيئاً حقيقياً؟**
تغطي السلوك لا التنفيذ: كلمة حالية خاطئة ← 422 ولا تتغير الكلمة؛ الجلسات الأخرى 401 والحالية 200؛ 429 بعد 5 محاولات؛ بدون جلسة 401؛ منظمة غير معتمدة ومشغّل منصة؛ أن صف التدقيق لا يحوي كلمة المرور؛ وللـ BFF: رفض Origin خارجي قبل أن يصل أي طلب للـ backend (`m.calls` فارغ). يمكن إثبات قيمتها بإزالة الإصلاح مؤقتاً ورؤية الاختبار يفشل (mutation check يدوي).

**س15: ما خطتكم لإغلاق بنود المرحلة الثانية؟**
مرتبة بالأثر والكلفة، لكلٍّ معيار قبول:
1. **تثبيت الأساس:** تشغيل كل شيء وإصلاح الفشل، تفعيل حماية الفرع. *القبول: CI أخضر إلزامي.*
2. **توسيع التدقيق** (`writeAudit` جاهز): الطلبات والملفات والأدوار وعضوية المشاريع + شاشة عرض للمدير. *القبول: اختبار لكل عملية يتحقق من الصف.*
3. **`DELETE /files/:id`** مع صلاحية وتدقيق وحذف من القرص وزر وتأكيد (لا زر دون endpoint). *القبول: اختبار backend + واجهة.*
4. **محدِّد معدّل مشترك** إن تقرر التوسع الأفقي. *القبول: اختبار بنسختين.*
5. **CSP بـ nonce** وربط Playwright في CI. *القبول: تقرير CSP بلا انتهاكات في E2E.*

**س16: ما الذي تغيّره لو بدأت من جديد؟**
أكتب CI الذي يشغّل اختبارات الـ backend منذ اليوم الأول (الفجوة الأخطر التي وجدها التدقيق: ~499 اختباراً لا تعمل تلقائياً)، وأفكّر في RLS لعزل المنظمات كطبقة دفاع ثانية، وأوحّد التدقيق كخدمة من البداية بدل توسيعه لاحقاً.

## أسئلة قد تُفاجئك + إجابات قصيرة
- **«هل العزل مثبت أم مفترض؟»** مثبت باختبارات تكامل (منظمة ← منظمة، مشروع ← غير عضو)، لكن في التطبيق لا RLS.
- **«لماذا 404 وليس 403؟»** كي لا يُستدل بوجود مورد لا يملك المستخدم حق رؤيته.
- **«هل الواجهة تفرض الصلاحيات؟»** لا، تعرضها فقط؛ الفرض في الـ backend.
- **«ماذا لو سُرق الكوكي؟»** HttpOnly يمنع القراءة عبر JS، وSecure في الإنتاج، والرمز قابل للإبطال، وتغيير كلمة المرور يُنهي بقية الجلسات.
- **«هل جرّبتم على PostgreSQL؟»** مجموعة الـ backend نعم (499 سابقاً)، أما e2e على PostgreSQL فلم يُشغَّل بعد — وهذا مصرّح به في README.
